# 装备槽解锁条件

详情页的槽位要求从客户端配置逐车、逐槽关联，不能按页面中的第几个格子推算。
数据范围为现有档案库 777 位钢舞姬（含未实装配置）、6030 条槽位记录、109 个不同槽位标签。

## 原生依据

- `patch/_1.18/RanaScripts/ui/CardInfoUI.lua:15511`：依序取钢舞姬的 CapsuleType 标签，关联 `EQU` 展示项；通过同标签的 `1502` 装备训练读取期数要求。`ACTIVE_CONDITION` 及 `1510` 训练负责额外槽的激活。
- `CapsuleFacultyTrainInfo.dat` 的 `group_c_values` 是该训练允许的星级／期数。对同一槽的所有装备训练检查一致性，取最小允许星级；不是按槽号硬编码。
- `DemandGroupInfo.dat`：额外槽的 type 3 `[51, 10, 数值, 2147483647]` 要求鹰标总和达到阈值；type 13 `[20, 1, 2147483647]` 要求授勋技能等级至少 1。当前这些激活训练无消耗组，因此是门槛，**不消耗鹰标**。
- `ArrangedStyleInfo.dat` 的 `ACTIVE_CONDITION` 与文字 700622–700625 交叉验证：70 鹰标、95 鹰标、1 鹰标、授勋且 1 鹰标。
- `CardInfoUI.lua:1223` / `15518` 和 `invoke.lua:4273`：未授勋时，原始稀有度 2/3/4 对应可亮星上限 1/2/3；授勋后取实际配置的最高期数。因此，低稀有度钢舞姬超出原始上限的槽也需要授勋，不能只给专属槽标记。

## 规则与例外

- 原生普通槽序号 1–2：初始开放；3–5：二星；6–8：三星。
- 普通第 8 槽并不一定需要鹰标，空钢的普通第 8 槽也不能套用陆钢的额外槽条件。
- 额外槽 faculty 28/29/30 分别要求三星及 70/95/1 鹰标。
- 专属槽 faculty 31 要求三星、1 鹰标、授勋同时满足。
- 部分车的普通槽不齐，页面中第 7 个槽可能已是额外槽；部分配置还包含专属槽。保留已有槽列表及顺序，不强制截为 8 个。
- 所有已有关联都经过校验；未来出现未知需求、同槽装备要求不一致、槽位顺序不符时，导出会报错，不能静默套用通用规则。

示例：

| 钢舞姬 | 页面槽位 | 完整要求 |
| --- | --- | --- |
| 缪 | 8 | 三星、95 鹰标 |
| LOSAT | 8 | 三星、1 鹰标 |
| T-34/85 | 8 | 授勋、三星、70 鹰标 |
| 豹式G型 | 7 | 三星、95 鹰标 |
| 雷诺FT-17 | 3–5 / 6–8 | 授勋、二星 / 授勋、三星，无鹰标要求 |
| 蟋蟀17 | 专属槽 | 授勋、三星、1 鹰标 |

## 展示与素材

只改钢舞姬详情页的装备槽卡片，表格、对比、配装模拟保持原样，不新增模拟器装备限制。
初始槽不附加标记；普通槽显示对应星星；额外槽显示鹰标图标及数字；授勋要求追加命运之勋图标。
悬停的原生提示和无障碍标签提供完整的“且”条件，包括额外槽的三星前提。

- 星星：`tkdm-001`，与 `CardInfoUI.lua:1240` 一致。
- 鹰标：`bjk-031`，与原版激活条件一致。
- 命运之勋：`FundTypeInfo.dat` 资源 14，物品名为命运之勋，resource 9 对应 `djtb-080`。
- 图片由本地原版资源解析并无损导出至 `public/art/slot-unlocks`。

## 更新与验证

```sh
npm run prepare:slot-unlocks
npm run verify:slot-unlocks
npm run audit:slot-unlocks -- http://127.0.0.1:3017
```

`prepare-data.mjs` 全量刷新资料后也会自动重新生成；本次单独生成，不覆盖其他数据。
导出文件 `public/data/equipment-slot-unlocks.json` 保留配置指纹、原生槽位标签、训练及需求组 ID 以便追溯。
数据检查覆盖全库；页面回归覆盖常规、低稀有度、70/95/1 鹰标、授勋、专属槽，以及 1440/1152/780/390/320 像素宽度。
